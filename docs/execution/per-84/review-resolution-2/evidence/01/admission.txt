+## Review workflow
+
+Reviews follow a split-responsibility model: a review orchestrator (a
+separate agent from the executor) runs each review, and every review
+stage pairs a **finder** with a **refuter**, both run with clean context
+so neither inherits the other's biases.
+
+### Roles
+
+- **Review orchestrator** — reads the Card in flight, composes each
+  finder's brief, spawns finders and the refuter, then evaluates the
+  findings and refutations to determine what is written to the Card.
+  The orchestrator is the only role that writes to the Card. Only
+  adjudicated work reaches the executor, and only in its narrowed form.
+- **Finder** (`agents/review-finder.md`) — one per review axis. Finds
+  defects; reports findings meeting the bar below. Never writes to the
+  Card; reports to the orchestrator.
+- **Refuter** (`agents/review-refuter.md`) — one per review. Attacks
+  every finding against the repository and the Card; never adds or
+  softens findings. Never writes to the Card; reports to the
+  orchestrator.
+
+The definitions in `agents/` are canonical and harness-agnostic.
+Harness adapters (e.g. `.pi/agents/` symlinks for the pi subagent
+extension) are thin views over them and carry no content of their own.
+
+### The finding bar
+
+A finding is reportable only if it is all of:
+
+1. **Substantiated** — exact `file:line` evidence plus the exact rule,
+   ticket line, convention ID, or Card entry it violates.
+2. **Required** — fixing it is necessary for the change to be correct,
+   safe, or conformant. Preferences and hypotheticals are not findings.
+3. **Non-trivial** — anything the repo's tooling already enforces is
+   out; a competent engineer reading the evidence would agree the
+   change is worse if the issue stayed.
+
+Findings carry **severity** (how bad if real), never priority (the
+operator decides order).
+
+### Review types per stage
+
+Review types are settled per stage and listed here. A stage without
+listed review types has none settled yet; the orchestrator composes
+the review from what is listed, nothing more.
+
+**Code execution** — reviewing code produced by an implementation
+stage:
+
+- Spec-blind finders (receive the diff and brief-named sources, never
+  the spec):
+  - **Complexity**
+  - **Quality** — including error handling and failure behavior
+  - **Security** — including hostile input and failure modes
+  - **Language standards** — idiomatic adherence for the toolchain
+  - **Codebase standards** — `conventions.md` C-IDs, repo patterns
+- Spec-aware finders (additionally receive spec material from the
+  Card — typed skeleton, execution plan, governing decisions — per the
+  single-Card principle):
+  - **Spec adherence** — implements what the ticket asked, and only
+    what it asked (missing requirements and scope creep)
+  - **Test adequacy** — does the suite pin the accepted scope's
+    behavior
+
+**Planning** — reviewing artifacts produced by the planning stage:
+
+- **Execution plan** — the last gate before implementation. A
+  permissive, all-systems-go review: it asks only "must this plan not
+  proceed as written?" and flags nothing else. Findings are limited
+  to:
+
+  1. **Spec deviation** — the plan implements something the agreed
+     spec does not ask for, or omits something it requires outright.
+  2. **Referent deviation** — the plan contradicts the approved typed
+     skeleton, a recorded operator decision, or the Card's governing
+     rulings (cite the sequence).
+  3. **Executor capability** — the plan does not name the agent that
+     will execute it, or the work the plan demands exceeds the named
+     executor's capability: task complexity and detail must fit the
+     agent class proposed to carry it.
+
+  Explicitly out of scope for this review: better orderings, style,
+  risk notes, improvement suggestions, and any finding whose fix
+  leaves the plan's shape intact. A finding here is a claim that the
+  plan must not proceed; if the plan can proceed without the change,
+  it is not a finding.
+
+  Findings — or, when there are none, an explicit no-findings record —
+  are posted to the Card per the recording rules.
+
+No other review types have settled for this stage yet.
+
+### Refutation
+
+The refuter attacks every finding against the repository and the Card.
+The refuter treats the Card and the repo's documented standards as
+authority: a finding contradicting a recorded operator decision is
+refutable by citing the Card sequence. Verdicts are exactly REFUTED,
+SURVIVES, or PARTIALLY SURVIVES (original wording withdrawn, replaced
+by a strictly narrower claim).
+
+### Recording results
+
+Only the review orchestrator writes review results to the Card. Both
+the findings **and their refutations** are recorded — refuted findings
+are preserved with their refuting evidence, not discarded — following
+the established entry conventions: findings as stage-events keyed by
+finding ID, with axis, finding, and counterexample; verdicts and
+closures keyed to the IDs they close. The orchestrator's adjudication
+(what survives, in what narrowed form) is recorded as a decision.
+
